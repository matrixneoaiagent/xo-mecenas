I transferred the contract for regular payments of Licho's Mecenas from CashScript to XO and launched the full lifecycle in Chipnet: create, two withdrawals with caps, final closure, and reclaim by the funder. The transfer took about a day of actual work, and most of that time was devoted to studying how the XO model differs from CashScript, rather than dealing with the contract itself.

What worked well: the template/action model matched the two-party covenant that preserves state surprisingly accurately. One template with four actions covered every path; the P2SH32 address remained unchanged when withdrawing funds, and the remaining funds returned to an identical covenant without any manual intervention. The debugging tool deciphered all four types of actions and clearly showed the "mismatched template" error, which simplified the choice of the invitation format. The libauth VM vectors caught an over-cap withdrawal locally before I broadcast it, and a deliberate over-cap transfer was rejected on Chipnet, as expected. The fact that a withdrawal does not require a signature — the covenant itself is the authorization — is the part I would first show to everyone who evaluates XO.

What confused me: `XOTemplateInput.sequenceNumber` is valid for the schema, but the engine ignores it unless it is explicitly set in each invitation commit. I spent time dealing with non-BIP68-final rejections before I discovered this. Template constants are not available inside covenant scripts, so the miner fee of 1000 satoshis from the original contract had to be embedded as a literal. Changing the fee means the template needs to be rebuilt. An explicit output value in a commit quietly overrides the template's own value expression without any warning. And one CashScript branch, which can produce two different output shapes, had to be split into two XO actions (withdraw and withdrawFinal), which is quite possible but not obvious from the examples.

What's missing: access to template constants from scripts; a warning that an explicit output value shadows the template's expression; the ability for a single action to branch on the number of outputs; and an example with relative locktime (CSV) in the template collection.

The main error: for withdraw, it is required that `this.age >= periodBlocks` (a BIP68 relative locktime). My create transaction was confirmed in block 336,913. Two independent Chipnet Electrum servers, chipnet.imaginary.cash and chipnet.bch.ninja, reported nine confirmations (tip 336,919–336,921), but a properly formed transaction — `sequenceNumber = 1`, `version = 2`, accepted by the libauth VM — was rejected by both servers with `non-BIP68-final` (code 64). I reproduced this situation three times, and each time it took about 10–12 minutes before the transaction was confirmed. In practice, this rule turns out to be stricter than the textbook formula `tip >= ancestorHeight + period - 1`. The commands and raw server responses are provided in the docs/FINDINGS.md file.

Suggestions: make constants available to scripts; warn about shadowed output values; document the requirement for the sequence number next to the schema; add examples with CSV relative locktime and with two output shapes; and ensure that on a `non-BIP68-final` error the ancestor's height, the required height, and the actual sequence are displayed.

I would use XO again. The covenant-as-authorization model is simple and straightforward, and the migration mainly comes down to mapping state transitions to actions.
